## 三、🔴🔴 最关键的发现：「涨停池 0 票」的真正原因

### 3.1 我之前的解释是错的

我上一份报告说：**「网络抖动 → 熔断 → 拿不到数据」**。

**实测推翻了这个解释**（刚刚跑的同一个端点）：

```
limit_up_pool: rows=52   ← 现在完全正常！带 date_ms / 不带 date_ms 都是 52
  样例: ST豆神(2连板,封单1165万) / 马矿股份(首板,封单4465万,涨停原因:铁精粉+采选扩能)
limit_break_pool: rows=33
limit_down_pool: rows=17
```

**而且我验证了 `date_ms` 参数是生效的**（不是被忽略）：
```
date_ms=2026-11-03: rows=52  first=ST豆神  last=龙版传媒
date_ms=2026-10-30: rows=49  first=新乳业    last=*ST航图
date_ms=2026-09-01: rows=83  first=开开实业  last=中广天择
```
**三个日期返回不同的股票 → 端点按日期过滤正常工作。**

### 3.2 真正的机制：熔断器是**按端点名**开的，但请求带了不同参数

关键日志：
```
19:58:17 [HiThinkLimiter] special_data.limit_up_pool 调用失败 (attempt 1/3)
19:58:20 [HiThinkLimiter] 熔断激活 reason=连续 5 次失败 special_data.limit_break_pool cooldown=30s
```

**注意熔断的 reason 是 `limit_break_pool`，而失败的是 `limit_up_pool`。**

再看 20:05 熔断冷却结束后：
```
20:05:04 [HiThinkLimiter] 熔断冷却结束，恢复调用
20:05:06 [HiThink 涨停上下文] 加载完成: 涨停 0 只, 炸板 34 只
```

> **🔴 决定性证据：同一时刻、同一次调用，炸板 34 只拿到了，涨停 0 只没拿到。**
> **而我刚才实测这两个端点都正常（涨停 52 / 炸板 33）。**

**为什么涨停拿不到、炸板拿得到？**

看 `core/p1_precompute.py:379`：
```python
df_lu = _to_frame(hithink_client.special_data_limit_up_pool(page=1, size=50))
```
**没有传 `date_ms`** —— 涨停池是「实时端点」，不带日期参数 = 拿「当前实时涨停池」。
而 `sync_special_today` 里的 `sync_limit_up_pool` **传了 `date_ms`**（带日期的历史口径）。

**19:45 之后 A 股已收盘**，实时涨停池可能已被服务端清空 → 返回 0。
**而炸板池用的是带日期的历史口径 → 拿到 34 只。**

### 3.3 所以真正的因果链

```
19:58:17  涨停池(不带 date_ms, 实时口径) 请求超时 → 重试 3 次全失败
          ↓
19:58:20  连续 5 次失败 → 熔断开启 (cooldown=30s)
          ↓
          熔断期间所有 HiThink 端点被一并挡下
          ↓
          P1 预计算: 涨停池 0 票 / 大盘温度 0
          ↓
20:05:04  熔断冷却结束
20:05:06  炸板池(带 date_ms) → 34 只 ✅
          涨停池(不带 date_ms) → 0 只 ❌  ← 不是熔断挡的，是端点本身返回空
```

> **结论：熔断（30s）是暂时的；真正让涨停池永远是 0 的，是 `p1_precompute` 用「实时口径」去调一个收盘后已经清空的端点。**
> **网络抖动只是让它在 P1 那一刻更彻底地失败。**

### 3.4 🔴 更深一层：就算取到了数据，也写不进库（ST-P0-13）

**这是我在 v2 中新发现的第二道闸门。** 复刻 `sync_limit_up_pool` 全流程后：

```
1) 原始 df: 52                                    ← 取数成功
2) limit_up_time 列存在: True
3) limit_up_time 转换 OK
4) 去空后行数: 52
   open_times dtype: float64   NaN数: 30/52      ← 52 只里有 30 只没开板数
   limit_up_time 样例: [None, None, None]         ← 时间戳字段全空
   industry none数: 52/52
```

**用真实 DDL（`open_times INT`，无主键）复现写入 → 静默失败：**
```
>>> _safe_save_df 返回: 0
>>> 表内行数: 0
```

**真正的报错（用最小用例复现）：**
```
Conversion Error: Type DOUBLE with value nan can't be cast because the value
is out of range for the destination type INT32
```

**三重问题叠加**：
1. `open_times` 是 float64 含 NaN → 绑 INT32 参数 → 抛 ConversionException
2. 表**没有主键** → 走 `executemany` 分支 → 逐行绑定，NaN 直接炸
3. `_safe_save_df` 的 `except` 只打 `logger.debug` → **异常被吞** → 返回 0 → 上层只看到「0 条」，日志里**一行错误都没有**

> **这就是为什么这个 bug 能藏这么久：取数失败有日志（网络错误），写库失败没有任何日志（被 debug 吞了）。**

**修复验证**：
```

修复后: _safe_save_df 返回 52，表内 52 行
样例: ('002827.SZ', '高争民爆', 2, 549678530.0, None)
```

## 十二、😴 ST-P0-24：笔记本自动睡眠把 daemon 冻住（08:00 体检那次的真因）

### 12.1 表面正常，实则昨夜主循环停了 ~5.5 小时

2026-11-04 08:00 体检 80/0/0 全绿、daemon 正常启动。但日志里藏着两次长中断：

```
2026-11-04 03:17:54 [LOOP_GAP] 主循环中断 2330.9s（39分钟）后恢复
2026-11-04 07:58:52 [LOOP_GAP] 主循环中断 16857.9s（4.69小时）后恢复
03:00 VACUUM：日志只有"调度器已启动"，从没有"触发定时维护"  ← 从未真正执行
```

### 12.2 根因：Redmi 笔记本自动睡眠

Windows 事件日志（Kernel-Power 566 多次转换）+ powercfg 确认：

| 项 | 值 |
|---|---|
| 机型 | XIAOMI Redmi Book Pro 14 2024（笔记本，PCSystemType=2） |
| 插电睡眠超时 | 180 分钟 |
| 电池睡眠超时 | 3 分钟 |
| 全项目 SetThreadExecutionState | **0 命中（无任何防睡眠机制）** |

**不是崩溃、不是代码 bug** —— 是笔记本空转后自动进入睡眠，把 daemon 一起冻住。
03:00 正落在睡眠窗口，所以 VACUUM 从没跑过。

### 12.3 为什么这是 7×24 交易系统的致命伤

醒来后 daemon 能补跑「晚间链」（有 catchup 窗口），但**盘中任务漏了就漏了**：

| 任务 | 补跑窗口 | 睡眠错过时 |
|---|---|---|
| **P2 竞价 09:26** | `catchup_minutes=0` | 直接跳过，不补 |
| **P4 尾盘五拍 14:31/36/41/46/51** | 精确分钟匹配 | 错过那一拍就没了 |
| P3 盘中 150s/拍 | 连续节拍 | 睡眠期间整段漏扫 |
| 03:00 VACUUM | — | 睡眠则不执行 → 版本链累积 |

### 12.4 修复（两层，均已落地）

**第一层：系统电源方案（已立即生效，当前 daemon 就受保护）**
```bat
powercfg /change standby-timeout-ac 0      :: 插电永不睡眠（0x0）
powercfg /change hibernate-timeout-ac 0    :: 插电永不休眠
powercfg /change standby-timeout-dc 30     :: 电池 30 分钟（原 3 分钟太危险）
powercfg /change hibernate-timeout-dc 60
```
验证：睡眠超时 AC=0x0(永不) / DC=0x708(1800s)；休眠 AC=0x0 / DC=0xe10(3600s)。
（Modern Standby S0 机型不通过 powercfg 暴露 LIDACTION，合盖行为由固件决定。）

**第二层：daemon 唤醒锁（治本，重启后生效）**
- 新建 `core/wake_lock.py`：Windows `SetThreadExecutionState(ES_CONTINUOUS|ES_SYSTEM_REQUIRED|ES_AWAYMODE_REQUIRED)`。
- `auto_sniper_daemon.main()` 在取得单实例锁后 `acquire_system_awake()`，`atexit` 注册 `release_system_awake()`。
- 效果：daemon 存活期间系统不因空闲睡眠；屏幕仍可熄灭、可关显示器。
- 实测：`acquire` 返回 True / `is_held`=True / `release` 后 False；语法+lint 通过；回归 171 PASS / 1 FAIL（占库所致，与改动无关）。

### 12.5 终极提醒

即使有唤醒锁，**请勿手动合盖/手动睡眠**（合盖行为在 S0 机型由固件决定，代码无法覆盖）。
生产部署强烈建议改用**台式机 / 服务器 / 常开小主机**，笔记本只作调试。
