## 一、系统概览

### 1.1 这是什么

小杰AI选股系统是一套**运行在你自己电脑上的 A 股短线选股工具**。

它做的事情，用一句话讲清楚：

> 每个交易日，把 A 股全市场 5000 多只股票过一遍（经市值 / 流动性初筛后约 2100 只进入打分），
> 按「什么时候买」分成 5 个时间档位输出候选，并且附带每只股票为什么入选、为什么落选的完整理由。

它**不是**行情软件，不做交易下单，不预测涨跌。它只做一件事：**从全市场里筛出「今天这个时间点值得看一眼」的股票，并把判断依据摊开给你看。**

### 1.2 为什么要分 5 个档

A 股短线交易的节奏是分时段的。同一个技术形态，在早盘 9:25 竞价、在上午 10 点、在尾盘 14:50、在收盘后，含义完全不同。

所以系统把选股拆成 5 个「档位」，每个档位对应不同的买入时点、使用不同的筛选条件：

| 档位 | 名称 | 买入时点 | 这一天筛几次 |
|---|---|---|---|
| **1 档** | 底仓池 | 收盘后建仓，次日持有 | 1 次（晚间） |
| **2 档** | 竞价池 | 09:25 集合竞价 | 1 次（09:26） |
| **3 档** | 盘中池 | 10:00–14:00 盘中 | 每 150 秒一拍 |
| **4 档** | 盘尾池 | 14:30–15:00 尾盘 | 固定五拍（14:31 / 36 / 41 / 46 / 51） |
| **5 档** | 盘后池 | 收盘后确认 | 1 次（20:05） |

这样你打开系统，看到的 5 张表就是「今天这一天，五个不同时间点分别该关注什么」。

### 1.4 核心技术特点

**① 全本地运行**
数据存在你自己硬盘的 DuckDB 文件里，不上传任何服务器。

**② 五档独立筛选**
每个档位有自己的「物理胸甲」（硬阈值筛选模块），互不干扰。

**③ 理由可追溯**
每只股票能查到「命中了哪条战法」「哪条闸门把它拦下来了」，不给你黑箱结果。

**④ 阈值全部可调**
所有筛选阈值集中在 `config.yaml`，有界面可以实时调参（策略实验室），不用改代码。

**⑤ 后台与前台分离**
定时任务由独立守护进程跑，网页只是看结果，不会因为你关标签页就停。

**⑥ 结果可回看（V29 新增）**
每条推送出去的信号都会记 `signal_log`，每天 18:30 自动回填它之后 T+1 / T+2 / T+5 / T+10
的真实收益，并按原子战法聚合出胜率表。**战法有没有用，从「猜」变成「查」。**

**⑦ 机器会说话（V29 新增）**
daemon 每 5 分钟写一行心跳（时间、PID、内存、DuckDB 占用、各档位最近成功时间），
每天 07:00 把过去 24 小时聚合成一份体检摘要推企微。异常时走独立告警通道，不混在信号流里。

**⑧ 数据先体检再统计（V29 新增）**
信号入库前先打 A 股数据质量标记（ST、涨跌停越界、停牌、新股、复权缺失、价格跳变等），
统计收益时自动排除不可信样本。**脏数据不会污染战法胜率。**

**⑨ 推送直接给执行价（V29 新增）**
企微卡片不再只给战法名，而是同时给出建议仓位、出场模板、战术止损价、止盈价位、最长持有天数
和铁律硬止损下限，**看到就能下单，不用自己再算一遍。**

**⑩ 数字是真的（Tier 2 · 2026-11-03）**
V29 只解决了「有没有记录」，Tier 2 解决的是「记下来的数字可不可信」。七件事：

| # | 升级 | 一句话说明 |
|---|---|---|
| 2.1 | **唯一成交口径** | `core/execution_model.py` 成为费用/涨跌停/整手/T+1 的唯一真值：佣金万 3 最低 5 元、印花税万 5 仅卖出、过户费十万分之 1、100 股整手。模拟盘与两条回测路径全部引用同一函数，不再各写一份 |
| 2.2 | **前视偏差显式化** | 主口径统一为 `buy_delay=1`（信号次日开盘成交）；曾用 `buy_delay=0` 的 3 条战法（01_一进二 / 02_黄金缺口 / 29_量比异动）保留 `legacy_lookahead_risk` 标记，旧数字放进 `legacy_delay0` 对照块，历史结论仍可追溯 |
| 2.3 | **不可成交与滑点夹逼** | 一字涨停买不进、一字跌停卖不出、`vol<=0` 视停牌；成交价夹在当日 `[low, high]`。回测输出 `fill_rate_pct` 与 `n_buy_blocked / n_sell_blocked` |
| 2.4 | **风险指标补齐** | Sharpe / Sortino / Calmar / VaR95 / 最大回撤，双口径：`risk_real`（真实）与 `risk_legacy`（旧） |
| 2.5 | **胜率升级为净收益 + 净超额** | `signal_pnl` 增 7 个净列（含对上证/深证/创业板/板块混合基准的超额），`strategy_effectiveness` 增 4 个净聚合列。**基准缺失一律 NULL，绝不用 0 冒充** |
| 2.6 | **负向战法亮红灯 + 优化器只建议** | P5-05A/B/C、P5-03A 直接标红（不等 200 条样本）；`net_weight_recommendation` 只给建议，`auto_apply` 默认 False，不改任何实盘权重 |
| 2.7 | **战法面板链路修通** | `build_ui_snapshot()` 补齐 15 字段契约，并与一次性快照路径分离；daemon 每晚 18:30 回填后端到端更新 UI 面板（此前该函数缺失导致 ImportError，回填流水线从未真正执行） |

**关于「净超额」的三个基准**：主板个股对上证、深市个股对深证、创业板/科创板对创业板指；
另给一个按板块加权的 `net_excess_blend_pct`。**基准数据缺失时该列为 NULL**——
这是设计，不是缺数据报警（宁可空着，也不给你一个假的 0 超额）。

完整执行证据见 `docs/TIER2_EXECUTION_REPORT_20261102.md`；字段契约见 `core/FIELD_CONTRACT.md` 的「Tier 2 字段契约」一节。
### 1.5 一次完整的使用流程（典型场景）

```
早上 08:50  →  守护进程自动跑：数据同步 + 早盘编排
早上 09:18  →  自动推送一条早盘简报到企业微信
早上 09:25  →  你打开网页，看到「2档·竞价池」已经出结果
              → 里面有 8 只票，每只写着为什么入选

早上 09:30  →  守护进程开始每 150 秒扫一次「3档·盘中池」
              → 网页上「3档·盘中池」表格自动刷新

中午 13:00  →  「3档·盘中池」持续更新

下午 14:31 →  守护进程切到「4档·盘尾池」扫描
              → 这是尾盘建仓的窗口

收盘 15:00  →  收盘

晚上 19:45  →  守护进程开始晚间链：同步数据 → 重建底仓 → 扫盘后池
晚上 20:30  →  数据库安全压缩

次日早上    →  你打开网页，「1档·底仓池」已经是昨晚算好的结果
```

这条链路你不用手动触发任何东西，只要守护进程开着，它会自己跑完。

### 1.6 它明确不做的事

| 不做 | 说明 |
|---|---|
| 不下单 | 不连接任何券商接口，不自动买卖 |
| 不预测涨跌 | 只做条件筛选，不给「明天会涨」的预测 |
| 不给单一答案 | 同一天可能多个档位都命中同一只票，这是正常的 |
| 不替代判断 | 输出是候选清单，最终决策在你 |

## 三、五档选股池详解

这一章是整套系统的核心。每个池的逻辑都遵循同一个模式：

> **先做全局一票否决（ST、退市整理、停牌、市值过小、垃圾股……），再跑池内的若干条策略，任何一条命中就入池。**

否决在前，策略在后。这个顺序不能反，否则会出现「策略说很好，但它是 ST 股」这种漏网情况。

### 3.0 通用宪法

#### 3.0.1 五池共同遵守的硬性底线

| 规则 | 数值 | 来源 | 说明 |
|---|---|---|---|
| 最小流通市值 | 120 亿（1,200,000 万元） | `constants.STRATEGY_MIN_CIRC_MV_WAN`（旧名 `P1_SELECT_MIN_CIRC_MV_WAN`） | 太小市值波动剧烈，不适合短线；2026-09-26 由 140 亿下调到 120 亿 |
| ST / *ST 一票否决 | 强制 | `novice_guard.risk_hard_veto` | 新手保护，宁可错过不可错买 |
| 禁止行业 | 38 个 | `novice_guard.forbidden_industries` | 排除特定高风险行业 |
| 风险标签关键词 | 列表 | `novice_guard.forbidden_risk_tag_keywords` | 带这些标签的票直接拦 |

#### 3.0.2 「量」的口径统一（这一点很关键）

系统在多处提到「换手率」，全部统一使用**自由流通股换手率 `turnover_rate_f`**，而不是普通的 `turnover_rate`。区别在于：

- `turnover_rate` 按总股本算，大股东持股多时数值被稀释
- `turnover_rate_f` 只按自由流通盘算，更能反映真实筹码活跃度

如果实时数据缺失，系统会**用成交量反算**：`vol(手) × close / circ_mv(万元)`，绝不使用普通换手率降级。这个口径在 P2/P4/P5 三个池都被明确写进注释，因为如果口径混用，同一只票在不同池的结论会打架。

#### 3.0.3 「资金」的门槛也是动态的

主力净买、机构净买这类阈值，系统不写死金额，而是用：

```
门槛 = max(流通市值 × 比例, 市值阶梯地板)
```

原因是：10 亿市值和 500 亿市值，1000 万净买对前者是大单，对后者是零头。用同一个绝对金额判断毫无意义。

相关实现集中在 `core/strategies/fund_mv_utils.py`。

#### 3.0.4 战略赛道特殊待遇

电子、计算机、通信、国防军工、电力设备、汽车整车、医药生物、机械设备、基础化工、有色金属这 10 个行业
被定义为「战略赛道」（P2/P3/P4/P5 各自 `strategic_industries` 配置，与 `pool_manager.STRATEGIC_INDUSTRIES` 对齐）。

在 P3/P4/P5 三个池里，战略赛道的票会获得容错（bias 上限放宽、允许斜率 ≤ 0 通过）和加分。逻辑是：机构主导市场里，硬科技的长期资金逻辑和游资炒作不同，用同一套刻板阈值会误杀。

### 3.1 第一档 · 底仓池（P1）

#### 它是什么

这是**唯一一个隔夜池**。晚上算好，第二天开盘持有，目标是被动的、已经确认启动的股票。

#### 核心特征

| 特征 | 说明 |
|---|---|
| 运行时机 | 晚间 19:55 重建 |
| 持仓预期 | 1–3 天 |
| 三大档位 | 严格档 / 中性档 / 宽松档，可手动切换 |
| 数据依赖 | 完整日线，不依赖实时行情 |
| 观察池 | 连续无票或缩量高压时，引擎会填一个观察池（建议 ≤ 8%） |

#### 三档位的区别

底仓池是唯一支持「档位切换」的池，因为它的候选数量最多，需要按市场环境灵活调整严格度。

| 档位 | 什么时候用 | 效果 |
|---|---|---|
| 严格档 | 大盘强势（主升浪） | 阈值收紧，只留最好的 |
| 中性档 | 震荡市 | 默认档位 |
| 宽松档 | 大盘退潮 | 放宽阈值，避免空仓 |

档位不只影响阈值，还影响**整个评分基线**——切换档位时，评分公式的基线参数会整体切换，界面上会显示当前生效的是哪一档。

#### 评分维度

底仓池不只看单一指标，它综合多个维度打分（`score_calibration.compute_p1_multi_dim_smooth_score`），包含：

- 趋势健康度（均线排列、斜率）
- 量能配合（量比、成交额）
- 资金流入（主力、北向）
- 筹码结构（获利盘比例、集中度）
- RPS 相对强度（`p1_rps_calculator`，60 日周期）
- 机构资金记忆（`fund_memory_score`）

综合分 ≥ 及格线（默认 48 分）才入池。

#### 「洗盘」是什么

界面上「启动洗盘」按钮对应的动作是 `pool_manager.build_p1_pool_and_cache`——重新过一遍全市场，重建底仓并写入缓存文件。

这是 P1 最耗时的操作（要拉全市场日线算分），所以做了缓存，网页打开时不用每次重算。

### 3.2 第二档 · 竞价池（P2）

#### 它是什么

09:25 集合竞价结束时看一眼，决定 09:30 开盘买什么。**这是全天时间最紧的一次决策**，只有 5 分钟准备。

#### 运行机制

- 定时：每天 **09:26** 跑一次（与 09:18 早盘简报合并，错峰避免拥堵）
- 数据：昨日（T-1）完整日线 + 今日竞价快照
- 单票计算复杂度 O(1)，全市场一遍扫完

#### 四条策略（P2-01 ~ P2-04）

| 编号 | 名称 | 核心条件（按当前 `config.yaml`） | 通俗解释 |
|---|---|---|---|
| **P2-01** | ★主升浪确认 | 昨日获利盘 > 80%、开盘 > 昨日 cost_95th 且 > 昨日 high_20、竞价涨 1–3%、今日量比 ≥ 1.8、昨日 ATR ≤ 8%、竞价额未相对昨日全天萎缩（阈值 5%） | 筹码已高度获利，今早高开续攻 |
| **P2-02** | ★机构连贯发力 | 昨日涨 4–6%、昨日 MACD 柱 > 0、昨日量比 ≥ 1.8、昨日主力净额 ≥ 0、开盘 > MA5、竞价涨 0.5–2.5%、vol_ma5 上穿 vol_ma20 | 机构连续两天在买 |
| **P2-03** | ★无尽苍穹 | MA5 > MA20 > MA60、机构净买连续两日达动态门槛、竞价涨 1–4%、预估开盘换手 > 1.2%、昨日长上影 ≤ 2.5% | 筹码几乎全部获利，浮筹极少 |
| **P2-04** | ★底仓重金点火 | 流通市值 > 500 亿、近 20 日涨停 1–2 次、主力净额达动态门槛、竞价涨 2–4%、强度值达动态门槛、开盘 > 昨日 cost_50th | 大票被大资金点燃 |

四条策略是**或**的关系：满足任意一条就入池，并在池里打上对应的原子战法 ID 标签。

> 曾经的 `P2-05 板块异动跟随` 已彻底删除（代码文件、注册表、打分注入点全部移除），当前 P2 只在跑上述 4 条。

#### P2 特有的防误杀设计

有一个细节值得说明：命中 P2 核心筛选后，系统会**放宽** `strict_golden_burst_ok`（严格金门禁）的硬门槛。

原因写在源码注释里：如果不放宽，「策略三 0.5% 高开」这种本来合理的形态，会被金门禁误杀。

这体现了系统的取舍逻辑——宁可放宽一个通用门槛，也要保证 P2 筛出来的票真的能用。

#### P2 的「量纲陷阱」

源码里有一段专门的注释警告：TuShare 日线成交额通常是「千元」，而竞价快照的 `amount` 可能是「元」。量纲不一致时，「额萎缩」检测**不强行否决**，避免误杀。

这是很稳妥的做法——不确定就不下判断。

### 3.3 第三档 · 盘中池（P3）

#### 它是什么

**全天扫得最频繁的池**。从 09:30 到 14:00，每 150 秒重新扫一遍全市场。

#### 运行机制

- 每秒只跑一个「时钟对齐」函数（O(1)，几乎不耗资源）
- 真正的全市场扫描每 150 秒一拍（允许时段：09:30–11:30、13:00–14:30；14:31 起进入 P4 优先走廊，P3 让路）
- 只访问每只股票的 `tail(5)`，不做全表扫描

#### 防镰刀优化（V26.88 重点）

| 1 | 拥挤过热阈值收紧 | 普通 2.5 / 强势 3.5 / 龙头 4.2 量比上限（`config.yaml → strategies.p3.crowding_*_vr`） |
| 2 | 板块超额强度因子 | 区分龙头 / 跟风 / 幽灵股 |
| 3 | 强化跟风惩罚 | 板块跟涨的不给分 |
| 4 | 独自点火惩罚 | 没有板块支持的孤军奋战降权 |
| 5 | 早盘冲高回落检测 | 高开低走的直接拦 |
| 6 | 尾盘异动识别 | 尾盘突然拉升要谨慎 |
| 7 | 北向资金因子（已退役） | 2026-10-18 起随 hk_hold 数据源下线，不再参与评分 |
| 8 | 战略赛道加成 | 10 个战略行业（电子 / 计算机 / 通信 / 国防军工 / 电力设备 / 汽车整车 / 医药生物 / 机械设备 / 基础化工 / 有色金属）享受放宽与加分 |

### 3.5 第五档 · 盘后池（P5）

#### 它是什么

收盘后的最终确认池。用完整的当日日线数据，判断哪些票值得进明天的候选。

#### 实现方式特殊

P5 是**唯一用向量化实现**的池（其余池是逐票循环）。原因很简单：P5 在收盘后跑，这时候没有实时压力，可以一次算完整个市场，大幅缩短耗时。

源码注释里，P5-15（HighTightFlag，源自 Sequoia-X）标了它和其他策略的区别：

参数是扫了 94 日底池内 6808 个样本定出来的，注释里还记了结论：「1.3 / 1.25 / 缩量 0.7 → 5 日 +0.92%、10 日 +1.29%（超额），日均约 5 只」。

#### P5 的三层防伪

P5 还有三个额外机制：

**① 均线动能补偿**
健康乖离带内的票不会因为乖离小被扣分，斜率大的反而加分（1.25–1.4 倍）。

**② VWAP 惩罚**
盘后只有静态日线，分时结构丢失，所以用 VWAP 偏离度做最后一道防线：
- 软偏离 > 1.8% → 惩罚
- 硬偏离 > 3.5% → 乘数降到 0.55（几乎废掉）
- 尾盘 15 分钟内尖峰 > 1.2% → 额外乘 0.72

**③ 防飞刀（防镰刀）**
- 换手 > 8% 且涨幅 < 1% → 疑似出货，直接拦
- 板块 beta < 0.9 → 逆势票，拦

## 四、数据底座与字段契约

### 4.1 为什么用 DuckDB

整个系统的数据存在**一个文件**里：`data/quant_data.duckdb`（约 256 MB，2026-11-17 实测）。

选它而不是 MySQL / SQLite 的原因很实际：

| 特性 | 说明 |
|---|---|
| 单文件 | 备份就是复制文件，迁移就是拷文件 |
| 嵌入式 | 不需要起服务，不会占端口，不会被别的东西抢连 |
| 列式分析 | 算 2000 只股票 × 120 天的均线，是它的主场 |
| 并发模型简单 | **全机只允许一个进程写**，天然避免抢锁 |

### 4.2 单进程写约束（必须理解）

> **DuckDB 全机单进程写。**

意思是：同一时刻只能有一个进程写这个数据库。这条约束是硬性的，因为 DuckDB 的文件锁在多写场景下会直接崩。

系统里的角色分工：

| 进程 | 对数据库的权限 |
|---|---|
| `auto_sniper_daemon.py`（守护进程） | **写** |
| `streamlit run ui/app.py`（网页） | **只读** |
| `streamlit run run_lab.py`（实验室） | **只读** |

如果需要维护（VACUUM 压缩），必须先让守护进程让路：

```
1. 开维护锁（master_control.json 的 maintenance_mode = true）
2. 守护进程检测到维护锁，跳过所有写库任务
3. 释放当前进程的读连接
4. 执行 duckdb_vacuum_silent()
5. 关维护锁
6. 重启守护进程
```

界面上对应的按钮就是侧边栏的「🛠 停Daemon→压缩→重启」和「🚨 一键强制数据库维护」。

### 4.3 连接管理

`data/db_core/_connection.py` 提供三种连接：

| 函数 | 用途 | 特点 |

### 4.9.1 数据质量标记层（V29 新增）

`data/data_quality_flags.py` 在信号写入 `signal_log` **之前**先给每条信号打一组标记。

#### 10 类标记

| 标记 | 含义 | 是否排除出收益统计 |
|---|---|---|
| `ST_STOCK` | ST / *ST / 退市整理 / 风险警示 | 否（照常统计，但涨跌停按 5% 判定） |

| `NEW_STOCK_SUBSET` | 上市不足 60 个交易日，波动不具代表性 | **是** |
| `SUSPENDED` | 信号日停牌（收盘=前收盘）或零成交 | **是** |

| `PRICE_JUMP` | 收盘价相对前收异常跳变（数据错位） | **是** |
| `NO_QUOTE` | 无行情（无收盘价） | **是** |
| `LOW_LIQUIDITY` | 成交额低于 10 万，价格信号不可信 | 否 |
| `QUALITY_UNRESOLVED` | 标记过程异常（信号照常入库，不阻塞） | **是** |

| 板块 | 代码前缀 | 涨跌停幅度 |
|---|---|---|
| 沪市主板 | 60xxxx | ±10% |

| 创业板 | 300/301 | ±20% |

#### 为什么必须有这一层

新股上市初期波动本就不稳定，停牌日价格是假的，复权错位会让涨幅算成天量。

### 4.9.2 信号落库与 T+N 收益回看（V29 新增）

#### 信号落库：`data/signal_logger.py`

每次五档任一池推送出票，都会写一行 `signal_log`，字段覆盖：

| 字段组 | 内容 |
|---|---|
| 身份 | `id`、`signal_uid`、`trade_date`、`log_date`、`ts_code`、`name`、`pool` |
| 战法 | `strategy`（人话串）、`strategy_ids`（原子 ID 数组）、`strategies`、`strategy_low_conf` |
| 评分 | `score`、`pool_score`、`burst_score`、`regime`、`score_breakdown` |
| 入场 | `push_price`、`pre_close`、`entry_basis`、`rank_in_pool`、`is_observation`、`pushed` |
| 风控 | `exit_template`、`suggested_position`、`stop_loss_price`、`stop_loss_pct`、`take_profit_half_price`、`take_profit_full_price`、`max_hold_days` |
| 质量 | `data_quality_flags` |

#### 收益回看：`data/signal_backtest.py`

每天 **18:30** 由 daemon 自动执行，做三件事：

1. **回填收益**：把每条历史信号在 T+1 / T+2 / T+5 / T+10 的真实收益写进 `signal_pnl`
2. **聚合战法胜率**：按原子战法 ID 汇总，写进 `strategy_effectiveness`
3. **出战法权重推荐报表**（V29.1 接入）：`optimize_strategy_weights(auto_apply=False)`，
   写到 `data/strategy_weight_recommendation.json`，**只统计、不改实盘权重**（详见 8.17）

四个关键设计（都是踩过坑之后定下来的）：

| 设计 | 为什么这么定 |
|---|---|
| 按**实际交易日**第 N+1 条日线定位 | 节假日、临时休市不会让 T+N 偏移到不存在的日期 |
| 用真实 **high / low** 算最大浮盈与回撤 | 只用 close 会低估波动，把回撤算得比实际小 |
| 无基准时 `benchmark/excess` 写 **NULL** | 拿绝对收益冒充超额收益是自欺欺人 |
| 被质量标记阻断的样本**直接排除** | 脏数据不进战法胜率 |
| 按 `log_id` 去重、跨 N 档不重复计数 | V29.1：同一条信号在 `signal_pnl` 里按 T+1/T+2 各一行，累加会把胜率稀释、样本虚高（详见 8.17） |
| 综合口径只用**最新已成熟档位** | 缺 T+5 时自动回退 T+2/T+1，而不是让报表空转 |

#### 入场价的两种口径

历史信号有两种来源，必须区分清楚，否则收益算的是假的：

| `entry_basis` | 含义 | 条数（生产库实测） |
|---|---|---|
| `push_price:p5` / `push_price:p3` | 当场推送时的真实成交价 | 27 条 |
| `backfill:close` | 历史行没有推送价，用信号日当天**真实收盘价**补齐 | 63 条 |

补价逻辑只补 `push_price IS NULL` 或 `<= 0` 的行，**已有值一律不覆盖**；
行情缺失就留空，**绝不用前收盘或次日价格顶替**。

#### 生产库实测产出

| 项 | 数值（2026-11-01 只读复核） |
|---|---|
| `signal_log` | 120 条，覆盖 7 个交易日（2026-10-08 ~ 2026-10-21），id / signal_uid 均唯一 |
| `signal_strategy_ledger` | 302 条（`(signal_uid, strategy_id)` 全部唯一，孤儿行 0） |

**为什么 T+10 现在是 0 条**：行情库最新交易日为 2026-10-21，
10-21 之后没有新交易日，T+10 窗口尚未走完。
**这是正确的行为 —— 系统宁可空着，也绝不伪造收益。**

样例（真实计算结果）：

| log_id | T+1 收益 | T+2 收益 |
|---|---|---|
| 1 | +0.234% | +0.995% |
| 2 | -1.522% | -3.332% |
| 3 | +10.847% | +20.106% |

### 4.9.3 原子战法 ID 规范层（V29 新增）

`core/strategy_id_registry.py` 解决一个很具体的问题：

历史 `signal_log` 里的战法字段长这样：

```
观察 / 分时偏弱 / 趋势确认较强，延续更顺 | 主线保送 | 黄金十绝 | P5-05C·趋势确认 P5-05B·趋势质量 P5-05A·趋势结构
```

其中只有 `P5-05A / P5-05B / P5-05C` 是**可统计的原子战法**，
其余全是描述性文案。如果直接按整串聚合，一条信号会被拆成十几个战法，
每个都只有 1 条样本，胜率毫无意义。

| 函数 | 作用 |
|---|---|
| `parse_atomic_strategy_ids()` | 从任意文本抽出去重后的原子 ID 列表 |
| `parse_labeled_atomic_strategies()` | 抽出 `(ID, 中文标签)`，标签优先取 `ID·标签` 形式 |
| `canonical_label()` / `display_name()` | 规范标签与展示名 |
| `pool_of()` | 由 ID 前缀推断所属池（p1~p5） |
| `is_low_confidence()` | 判断战法串是否低置信（无原子 ID 或纯描述文案） |

这是一个**纯函数解析层**，不新增战法、不改策略、不参与任何过滤或打分；
解析失败一律返回空列表，调用方必须容忍空结果，保证推送主链路不受影响。

UI 顶部那颗「数据健康度」徽章，判据在本轮被纠正过一次：

| 字段 | 含义 | 是否用于告警 |
|---|---|---|
| `coverage_pct` | 最新日有行情票数 ÷ 全市场在市票数（现约 **25%**） | **否**，仅信息展示 |
| `breadth_pct` | 最新日有行情票数 ÷ **上一交易日**有行情票数（现 **102.6%**） | **是**，阈值 `< 85` |
| `tracked_prev_n` | 上一交易日有行情票数 | 参照值 |
| `mv_gate_yi` | 日线库市值闸（**120 亿**） | 文案说明用 |

**为什么换判据**：日线库**按设计**只抓总市值/流通市值 ≥ 120 亿的票
（`constants.DATA_FETCH_MIN_TOTAL_MV_WAN`、`data/fetcher/_indicators.py`），
所以 `1380 / 5576 = 25%` 是**正常状态**，不是缺数据。
旧版用 `<60%` 判据会**天天**误报，把真缺数据淹没在常态噪声里。
真正的健康度判据是「相对上一交易日有没有骤降」——掉到 85% 以下才说明同步中断或抓了半残日。

**UI 实际文案**：

```
[warning] **需关注** ｜ 最新交易日 2026-11-02（T-1） ｜
跟踪域 1380 只（较上一交易日 103%） ｜
daemon 最后日志 2026-10-22 15:06（287.0h 前） ｜
信号样本 p3=11 p5=132 ｜ 交易日历至 2026-10-21
```

**读库失败 ≠ 数据不可信**：体检优先用 `get_read_conn_singleton()`；
该连接在「库文件不可写 / 被占 / 无 ACL」时会失败（它走的是读写配置），
此时降级到原生 `duckdb.connect(read_only=True)`，仍读不到才判「读不到」。
理由见 `core/FIELD_CONTRACT.md` 硬约束 3：不能把 `data/db_core` 改成 `read_only=True`，
否则与进程内读写连接触发 DuckDB 配置冲突，会导致 `signal_log` 落库失败。

## 五、守护进程与定时调度

### 5.1 为什么必须有守护进程

`ui/app.py` 是**纯事件驱动**的——按钮点击、页面展示、同步扫描。**它不包含任何后台定时器**。

这意味着：

- 刷新网页不会触发定时任务
- 多开标签页也不会
- **关闭浏览器，网页进程还在，但定时任务不在网页里**

所以定时任务必须由一个**独立常驻进程**承担，那就是 `auto_sniper_daemon.py`。

### 5.2 部署纪律

**全机只允许两个进程**：

```
1. auto_sniper_daemon.py    ← 后台大脑，负责所有定时任务
2. streamlit run ui/app.py   ← 网页，只读显示
```

启动用项目根目录的 `start_server.bat` / `start_server.sh`，它会按顺序起这两个。

也可以把 `auto_sniper_daemon.py` 单独设为开机自启（任务计划程序 / systemd / pm2）。

### 5.3 时区处理

**所有调度按北京时间触发**，与系统时区解耦。

守护进程启动时会做时钟自检：

```
北京时间 = 2026-10-12 12:00:00 CST
系统本地 = 2026-10-12 04:00:00 EDT
|Δepoch| = 0.000s   → 正常
```

判断逻辑用的是 **epoch 时间戳差**，不是显示字符串。所以即使你在美国时区，系统依然按北京时间跑，只是日志里的显示不同。如果 `|Δepoch| ≥ 3600 秒`，会告警提示检查系统时钟。


**关键设计：正常时完全静默。**
健康检查每小时跑一次，只有心跳超过 30 分钟没更新、24 小时零心跳、
某项任务失败时才会走告警通道，不会把告警混在普通信号流里造成噪声。

### 5.5 「允许补跑」是什么意思

比如 P1 重建允许补跑 240 分钟，意思是：**如果 19:55 因为断网没跑成，21:55 之前随时会重试**。

这让系统能容忍临时故障，不需要人工干预。

### 5.6 启动时自检

守护进程启动时会做一整套检查：

| 检查项 | 失败处理 |
|---|---|
| 单实例锁 | 已有实例运行时，**新实例直接退出** |
| DB 维护调度器 | 失败仅告警，不影响主功能 |
| HiThink 轮询器 | 未启用时静默跳过 |
| 时钟偏差 | 超阈值时告警 |
| data_fetcher 预热 | 失败仅告警 |

### 5.7 异常兜底

守护进程装了两个钩子，专门解决「进程莫名消失」的问题：

**① 全局异常钩子**
```python
sys.excepthook = _sniper_global_excepthook
```
任何未捕获异常立即写入 `sniper.log`，即使主循环挂掉也有证据。

**② 退出钩子**
```python
atexit.register(_sniper_atexit_log)
```
进程退出时打一行日志。**如果这行缺失，说明进程是被强杀或段错误，不是正常退出。**

这两行日志是排查「daemon 莫名不见了」的关键证据。

### 5.8 单实例锁

```
data/runtime/state/auto_sniper_daemon.lock
```

daemon 启动时尝试获取这个锁。获取失败说明已有实例在跑，**新实例立即退出**，避免双实例抢 DuckDB 写锁。

锁文件里存的是 JSON（含 `pid`、`started_at_human`、`cmdline_info`）。
V29 之后 `verify_system.py` 的单例锁检查也改成了**判 PID 是否存活**，
而不是「文件存在就报警」—— 所以 daemon 正常 24x7 运行时不会再被误报。

陈旧锁（进程已死但文件残留）会在下次启动时由 `core/process_orchestrator.py` 自动清理。

## 七、策略实验室

### 7.1 它解决什么问题

生产环境的阈值是「定好就不动」的。但你想知道：**如果这个阈值改成 50 会怎样？改成 60 呢？**

策略实验室就是干这个的。

### 7.2 启动方式

```bash
streamlit run run_lab.py
```

独立进程，不和指挥舱抢内存。

### 7.3 界面结构

#### 缩量观察池放宽（会话覆写）

三个参数，影响整个缩量上下文的判断：

| 参数 | 含义 | 默认 |
|---|---|---|
| 缩量量比上限 | 量比中位低于此值算极端缩量 | 0.95 |
| 豁免大盘市值下限 | 达到此市值的大中盘可走放宽换手 | 500 亿 |
| 资金正向下换手底线 | 缩量环境下换手率下限 | 0.52% |

> **重要**：这些是**会话覆写**，只写入 `session_state`，**不修改磁盘上的 `config.yaml`**。

#### 池选择器

五个池：底仓池 / 竞价池 / 盘中池 / 盘尾池 / 盘后池

切换后会渲染对应的全部参数滑块：

| 池 | 参数数量 |
|---|---|
| 底仓池 P1 | 9 个（strict / neutral / relaxed 三档，参数集相同） |
| 竞价池 P2 | 62 个 |
| 盘中池 P3 | 109 个 |
| 盘尾池 P4 | 64 个 |
| 盘后池 P5 | 91 个 |

> 口径说明（2026-11-01 实测）：P2–P5 的滑块数量 = 该池 dataclass 中「运行值为数值类型」的字段数
> （`strategic_industries` 这类 list 字段不渲染为滑块）。P1 不走 dataclass，
> 取当前 profile（strict/neutral/relaxed）允许的数值参数集合，三个 profile 均为 9 个。

每个滑块的标签都是中文的，还带默认值和允许范围：

```
底仓综合分及格线（1档）（默认 48，综合分低于此不入底仓池）｜允许 0～200
```

这个翻译由 `ui/strategy_lab_labels.py` 完成——把 `pass_line` 这种字段名变成人能看懂的话。

#### 两个执行按钮

| 按钮 | 作用 |
|---|---|
| 🚀 立即测试 | 用当前滑块值跑一次扫描，看命中数和最高分 |
| 🧬 开始全景扫描 | 选一个参数，让它从起始值扫到终止值，画出曲线 |

#### 全景扫描的产出

它画的是「参数值 → 命中数 / 最高分」的曲线，并给出一句提示：

> 💡 **架构师提示**：寻找【入池数】与【最高分】变化平缓的连续区间（稳健平原）。
> 若数据呈断崖式突变，即为过拟合悬崖，实盘禁用！

这是整套实验室最有价值的输出——**帮你找到参数的稳健区间，而不是最优点**。

最优值往往是个孤立的尖峰（过拟合），稳健区间才是能实盘用的。

实测举例（单点扫描，P1 池）：

```
参数 ma20_pregate_above_days = -998
→ 命中 33 只，最高分 86.1
```

### 7.4 参数边界与中文化

`ui/strategy_lab_labels.py` 做了三件事：

| 功能 | 说明 |
|---|---|
| `build_field_label()` | 字段名 → 中文标签 + 默认值 + 范围 |
| `bounds_for()` | 给定默认值，算出滑块的上下界 |
| `clamp_value()` | 把用户输入的值夹到合法区间 |
| `lab_input_step()` | 根据量级自动选合适的步长 |

自动步长这个设计很实用——`min_score` 这种整数量级的参数步长是 1，`bias_20` 这种百分比是 0.001，不会让你用同一个步长去调两种量纲的值。

### 8.1 五层信号过滤

`core/signal_filter.py` 是一个五层漏斗，每层解决一类问题：

|---|---|---|---|
| **L1** | 基础分过滤 | 技术面平庸的票 | 约 30% |
| **L2** | 资金真实性 | 无量上涨、对倒拉升等假突破 | 约 25% |
| **L3** | 异常形态 | 高位放量长上影、连续大阴线 | 约 20% |
| **L4** | 流动性溢价 | 流动性枯竭（换手 < 0.5% 或 > 15%） | 约 15% |
| **L5** | 基本面 | 基本面硬伤 | 视情况 |

每层返回 `(是否通过, 落选原因)`，原因会一路带到界面上——这就是你能在界面上看到「为什么不买」的原因。

```python
# core/signal_filter.py:34
def filter_layer1_base_score(score, breakdown=None):
    threshold = FILTER_THRESHOLDS["L1_base_score"]
    if score < threshold:
        return False, f"基础分{score:.1f}<{threshold}，技术面平庸"
```

注意它返回的是**中文原因字符串**，会直接显示在阵亡基因追溯里。

`core/exit_strategy.py` 定义四套出场模板：

### 8.7 评分权重体系

### 8.17 V29.1：反馈链完整接通（2026-10-13 修复）

上一轮（V29）把「回填」这一步做好了，但顺着这条链往下查，发现**下游两处是断的**，
表现为「回填表里有数据、战法推荐却永远是空的」。本节记录根因与修复口径。

#### 断点 1：优化器只读 T+5，而 T+5 还没成熟

| 项 | 内容 |
|---|---|
| 根因 | `core/strategy_weight_optimizer.py` 的 SQL 条件是 `n_signals>0 AND t5_win_rate IS NOT NULL`。系统初期只有 T+1/T+2 收益，`t5_win_rate` 全为 NULL，于是 15 条聚合行被全部过滤，优化器静默返回空 |
| 后果 | `data/strategy_weight_recommendation.json` 永远不生成，CLI 显示「无推荐条目」，看起来像「回填没生效」 |
| 修复 | 改读 `win_rate / avg_return / avg_max_drawdown`，并按 `N_DAYS_PRIORITY=[10,5,2,1]` 为每个战法选**最新已成熟档位**；T+5/T+10 未成熟时自动回退到 T+2/T+1 |

#### 断点 2：优化器从未被任何调度调用

代码注释写着「daemon 每日 17:30 调用」，但全仓搜索 `optimize_strategy_weights` 没有任何调用点，
属于「注释里的链路不存在」。现把它接进 daemon **已有**的 18:30 回填流水线，作为第三步：

```
18:30 SIGNAL_BACKFILL
  1) backfill_pnl()                          -> signal_pnl（T+1/T+2/T+5/T+10 收益）
  2) compute_strategy_effectiveness()        -> strategy_effectiveness（原子战法 × 池 × 档位胜率）
  3) optimize_strategy_weights(auto_apply=False) -> strategy_weight_recommendation.json（仅统计）
```

第三步强制 `auto_apply=False`：**只产出推荐报表，绝不改实盘权重**。

#### 顺带修掉的统计口径 Bug

旧版 `compute_strategy_effectiveness` 还有一个更隐蔽的问题：同一个 `log_id` 在 `signal_pnl`
里按 N 档各有一行（T+1 一行、T+2 一行……），旧代码

- 用 `n_signals = len(sub)` → 把 T+1、T+2 当成**两个独立信号**重复计数
- 用 `n_win / n_evaluated` 跨全部 N 档求和 → **同一条信号被算 2~4 次**

这会让胜率被系统性稀释、样本量虚高。现改为：

1. 每个 `(pool, strategy)` 组内先按 `log_id` 去重，得到唯一信号集合 → `n_signals`
2. 分档统计（`t1_win_rate` / `t2_win_rate` / ... 仍保留）
3. **综合口径只用「最新已成熟档位」统计一次**，不跨档累加
4. 幂等删除范围从「当天全部行」收窄为「当天 + 本次涉及的 (pool, strategy)」

### 8.18 V29.2：Streamlit 战法胜率面板（2026-10-13 新增）

前面 8.17 把「反馈链」接通了 —— 数据每天在流进 `strategy_effectiveness`，
但你只能靠 `python -m core.cli_view_recommendation` 看文字表格。
本节新增的是**图形化只读面板**：在 Streamlit 主界面底部，点开就能看。

#### 8.18.1 为什么是「快照」而不是直接查库

这是本节最关键的设计决策，先说清楚原因：

| 约束 | 说明 |
|:--|:--|
| DuckDB 单写锁 | Windows 下同一文件只允许一个进程独占打开（见 4.2） |
| daemon 常驻 | 实盘机上 daemon 24×7 跑着，Streamlit 是**第二个**进程 |
| 后果 | 面板若在每次 rerun 时 `duckdb.connect()`，直接撞文件锁报错 |

所以链路设计成**单向只读快照**：

```
daemon 18:30（唯一写进程，已持有 DuckDB 锁）
  1) backfill_pnl()                            -> signal_pnl
  2) compute_strategy_effectiveness()          -> strategy_effectiveness
  3) optimize_strategy_weights(auto_apply=False) -> strategy_weight_recommendation.json
  4) build_ui_snapshot()          [V29.2 新增]  -> strategy_effectiveness_ui_snapshot.json
                                                          ↓
                                    Streamlit 只读 JSON（不碰 DuckDB，@st.cache_data 30s）
```

好处：UI 不抢锁、rerun 极快、daemon 挂了面板仍能看上一版数据（带过期提示）。

#### 8.18.2 三个文件各干什么

| 文件 | 角色 | 说明 |
|---|---|---|
| `core/strategy_effectiveness_dashboard.py` | 读取层 | `load_snapshot()` 读快照 + NULL 安全 + 字段规范化；**全文不 import `data.db_core`** |
| `core/strategy_effectiveness_snapshot.py` | 生成层 | `build_ui_snapshot()` 原子写 JSON（先写 `.tmp` 再 `os.replace`，UI 不会读到半截文件）+ 采集近 30 天 `history` |
| `ui/strategy_effectiveness_panel.py` | 视图层 | 9 个渲染函数，入口 `render_strategy_effectiveness_panel()`；全程 `try/except` 包裹 |

#### 8.18.3 口径冻结（四条硬禁止）

面板**只**展示 `primary_n_days` 主口径，并在代码里物理执行这些禁止：

| 禁止 | 实现方式 |
|:--|:--|
| 不读 `t5_win_rate` 等旧字段 | `normalize_stats()` 里 `FORBIDDEN_FIELDS` 直接 `pop` 掉，UI 层拿不到 |
| 不跨 N 档相加 | `primary_n_days` 单值透传；`available/missing_n_days` 仅作文案 |
| 样本不足不下结论 | `classify_sample()` 只输出「零样本/偏少/中等/充足」四档，无「有效/无效」 |
| 不自动改权重 | `mode` 原样透传 `statistics_only`；面板无任何写库调用 |

平均胜率 / 平均收益一律用 `weighted_average()` **按 `n_evaluated` 加权**，
不用算术平均 —— 否则一个 1 样本的战法会把整体胜率拉飞。

### 8.20 V30：上证 / 深证 / 创业板 混合基准研究（2026-10-13 新增）

> 需求：「几个池选出来的股票在计算每日涨跌的时候，一定要把上证、深证和创业板的涨跌也放入一起研究。」
> 口径：**只做统计研究，不进入评分与选股决策**；不考虑北交所。

#### 8.20.1 为什么必须做

V29 之前生产库**根本没有 `index_daily` 表**，所以
`signal_pnl.benchmark_pct / excess_pct` 一直是 NULL，面板「平均超额%」整列是「—」。
也就是说系统从来没有回答过：**这只票 T+2 涨 3%，是大盘也在涨 3%，还是它真的跑赢了？**

更关键的是：只拿沪深300 一个基准会**系统性高估成长风格战法**。
一只有在创业板涨 5% 的票，在沪深300 跌 2% 的日子里会被判「超额 +7%」——
**赢了大盘 ≠ 赢了市场**。

#### 8.20.5 走查中抓到的 8 个真实 Bug

设计能跑通、单元测试能过，但**线上必然不出数**的一类问题。逐个都是"字符串比较"惹的祸。

| # | 现象 | 根因 | 修复 |

#### 8.21.2 三条硬教训

1. **`rolling(N).max()` 默认含当日。** 做「突破前 N 日高点」判定时，
   必须 `shift(1).rolling(N)` 或 `iloc[:-1].tail(N)`，否则条件数学上不可能成立。
   P5 早在 `p5_postmarket_screener.py:349` 就修过，P3/P4 一直没同步。
2. **跨模块传字段时，要确认上游真的产出这个键。** P4-07 读 `rt['vwap']`，
   但 pipeline 从没往 `rt` 里放过 `vwap`，于是 `if vwap > 0` 这条路永远走不通。
   正确的做法是从已有的 `amount` / `vol` 现算。
3. **`merge_daily_with_realtime` 会污染末行。** 任何「近 N 日」统计
   （持有率 / 回收次数 / 回看窗口）都要先判断末行是不是当日未收盘行。
   扫描层算「历史」时不算它，回看层算「历史」时必须算它——两种场景要分开。

### 8.22 模拟盘 · P3/P4 信号自动买卖实验（V29.3 ~ V30.5）

#### 8.22.1 它回答什么问题

系统最贵的不是代码，是「**不知道**」。最典型的一个「不知道」是：
**P3/P4 每天选出来的票，到底哪条战法真的有用？**

模拟盘用真金白银口径回答它：

- 买入价 = **信号行里的现价 + 滑点上浮 0.1%**（pipeline 写入的信号时刻真实价），**不是收盘价**
- 卖出价 = **触发阈值那一刻的实时价 - 滑点 0.1%**，**不是收盘价**
- 止损 **-3%（所有板统一）** → **100% 清仓，不看盈亏**
  - 【V30.11 起统一】不再按板差异化（创业板/科创板原为 -5%）——
    差异化会让宽止损的板块天然显得更优，**污染战法归因**
- 止盈 **+8%（所有板统一）** → 100% 清仓
- 最长持有 **10 个交易日**（`max_hold_days`）→ 到期未触发阈值则按收盘价强平
  - 与回测侧 `core/stop_rule_backtest` 共用同一份配置，保证「测的和跑的」是同一套规则
- 两条件同时触发 → 按 **STOP_LOSS 优先**（保守口径）
- 实验期 **100 个交易日**，到期停止新开仓，已有持仓继续按规则退出

### 8.22b 多层信号过滤器（五层，当前 shadow 观察期）

#### 8.22b.1 它是什么

`core/signal_filter.py` 的五层硬过滤，对**每条候选信号**逐层体检：

| 层 | 名称 | 拦什么 | 需要的数据 |
|---|---|---|---|
| L1 | 基础分 | 综合分 < 50（技术面平庸） | 综合分 |
| L2 | 资金真实性 | 主力净流出 / 换手过低（没量）或过高（出货）| 主力净流入、真实换手、量比 |
| L3 | 异常形态 | 上影线过长（抛压）、乖离 MA20 过大（追高）、连续阴线 | OHLC、乖离、连阴 |
| L4 | 流动性溢价 | 流通盘太小、换手不足、成交额太薄（买不进卖不出）| 流通市值、换手、成交额 |
| L5 | 基本面 | PE/PB/ROE 异常 | PE_TTM、PB、ROE |

#### 8.22b.2 为什么曾经是死代码，现在才上线

这套过滤器写完后**从未被扫描主链路 import 过**，一天都没生效。原因不是忘了，而是有真实风险：
- 缺字段时按 0 处理 → 会把**所有信号**判成不合格，一天清空
- L4 打分公式写死 `min(50, 市值/20)` → 要 **1000 亿市值**才满分，而本系统以中小盘动量为主，会误杀大批合格票

这两条都会导致「上线即事故」，所以当时选择不接。现在的做法是：
1. **缺数据跳过该层，而不是拒绝** —— 宁可放票，不可清空信号
2. **阈值全部可配置**（`config.yaml → signal_filter.thresholds`），已按实际候选池分布标定
3. **先禁用 → 再 shadow → 最后 enforce** 分三步走

#### 8.22b.3 上线前做了历史回放验证

用 122 条真实历史信号回放（`python tools/replay_signal_filter.py --full`）：

| 指标 | 结果 |
|---|---|
| reject 率 | **31.1%**（合理区间，不会清空） |
| 通过组平均净收益 | **−0.91%** |
| 拒绝组平均净收益 | **−3.40%** |
| 差值 | **+2.49%** |

**结论：被拒的票后续表现确实更差 → 过滤器有区分度，值得上线。**

#### 8.22b.4 当前状态：shadow（只看不拦）

```yaml
signal_filter:
  enabled: true
  mode: shadow      # 当前：只标注 + 统计，不拦任何票
  thresholds: {...} # 15 项阈值，已标定
```

**shadow 的实际行为**（已有回归测试锁定）：

| 模式 | 进入正式池 | 是否拦截 | 副作用 |
|---|---|---|---|
| `disabled` | 全部 | 否 | 无（与改造前完全一致）|
| **`shadow`** | **全部** | **否** | 不合格票写「风险标签」+ 累计 reject 统计 |
| `enforce` | 仅合格票 | 是 | 不合格票降级到观察池（`observation_only`）|

安全底线（均有测试覆盖）：
- 过滤器**抛异常时 pipeline 捕获并放行**，绝不阻断选股
- 缺数据时**跳过该层**而非拒绝
- `enabled: false` 时无论 `mode` 写什么一律禁用（一键回滚）

#### 8.22b.5 怎么观察、什么时候切 enforce

每次扫描结束，日志里会有一行（`grep signal_filter` 即可）：

```
[signal_filter][shadow] 总120 通过82 L1:28(23%) L2:5(4%) L3:5(4%)
```

判读方法：
- **总 reject 率 10%–50%** → 正常，继续观察
- **> 60%** → 阈值过严，会误杀好票，先用 `thresholds` 放宽
- **某一层占比异常高**（如 L2 拦掉 30%）→ 单独放宽那一层

切 enforce 的条件（建议同时满足）：
1. shadow 跑满 **3–5 个交易日**
2. reject 率稳定在 10%–50%
3. 抽查被拒票，确认「确实不该买」（而不是好票被误杀）

切换方式：`config.yaml` 里把 `mode: shadow` 改成 `mode: enforce`，重启 daemon。

### 8.23 战法有效性的两条链路（别混淆）

系统里有**两套**「战法有效性」机制，作用对象不同、口径不同：

| # | 链路 | 数据源 | 看什么 | 在哪看 |
|---|---|---|---|---|
| 1 | **信号回看**（T+N 事后收益） | `signal_log` + 日线 | 信号发出后 T+1 / T+2 / T+5 / T+10 的真实涨跌 | UI 底部「📊 战法胜率与权重反馈」；`core/strategy_effectiveness_ui.py` |
| 2 | **模拟盘实盘化** | `paper_order` | 真金白银口径下的净胜率、止损率、止盈率、平均持仓天数 | `ui/pages/1_模拟盘.py` → 🏆 战法排行榜 |

区别要点：

| 项 | 链路 1 信号回看 | 链路 2 模拟盘 |
|---|---|---|
| 性质 | 纸上事后统计 | 真实成交模拟 |
| 价格口径 | 收盘价 | 买入 = 信号时刻现价；卖出 = 触发阈值时刻实时价 |
| 费用 | 不计 | 佣金 + 印花税 + 过户费全扣 |
| 覆盖池 | P1~P5 全部五池 | 仅 P3 / P4 |
| 时间约束 | T+N 需等够交易日 | 需真实持仓天数积累 |

> 两条链路的样本会**重叠**，胜率不可直接相加或做差。
> 实践建议：**先看链路 2**——离真金白银最近，整手、T+1、涨跌停、费用全部算进去了；

#### A · 死因五层分级（新增 `core/p1_death_cause_registry.py`）

#### B-1 · MACD 柱量纲修正（绝对值 → 相对股价百分比）

MACD 柱的量纲是**元**，随股价线性放大，而旧闸门用的是**绝对值**比较。结果是同一条阈值对不同价位完全是两套标准：

| 股价 | 柱 -0.13 元 | 相对股价 | 现状判定 |
|---|---|---|---|
| 5 元 | -0.13 | **-2.60%** | 轻易被砍（得冠） |
| 100 元 | -0.13 | **-0.13%** | 几乎砍不到（放过） |

即：**低价股被得冠、高价股被放过**，而这两类恰好都在 P1 池里。

标定方法（`tools/probe_macd_bar_kill_scale.py`，40 个有效交易日、流通市值 ≥120 亿、全市场样本池）：按现状淘汰分位反推等效百分比阈值，构造上保证总体淘汰率与现状一致，**不引入任何人为权重**。

| profile | tier 0 | tier 1 | tier 2 |
|---|---|---|---|
| strict | -0.4268% | -0.5652% | -0.6930% |
| neutral | -0.5547% | -0.6665% | -0.7715% |
| relaxed | -0.6180% | -0.7182% | -0.8123% |

- 样本池总体淘汰率差：**0.00 pp**（构造等价）
- 逐交易日淘汰率差最大：**4.42 pp**（目标 ≤5pp，PASS）
- 翻转型态集中在低价/高价两尾：<10 元段 **+15.02pp**（加硬）、≥100 元段 **-11.66pp**（放松）

落地方式：`config.yaml` 三 profile 各新增 `macd_bar_kill_pct`，**旧 `macd_bar_kill` 全部保留**；`core/config_manager.py` 新增校验解析（长度≥3、全负、单调不增，任一失败返回 `None`）；`single_stock.py` 无 pct 配置时**自动退回旧绝对值判定**。

**Shadow 差集留痕（不自动生效）**：`data/runtime/p1_macd_gate_shadow.jsonl` 记录新旧口径判定不一致的样本，超 5MB 自动轮转。只写本地 JSONL，**不碰 DuckDB、不改权重、不改历史数据**；任何写入失败静默吞掉。

#### B-2 · 股性呆滞换手阈值连续化（硬阶梯 → smoothstep）

`single_stock.py` 与 `fund_mv_utils.py` 各有一份**硬阶梯**，断点处阈值跳变：

```
 999 亿  → 底线 1.50%
1000 亿  → 底线 1.05%    ← 同一只票，市值涨 0.1% 就换了一套标准
1999 亿  → 底线 1.05%
2000 亿  → 底线 0.65%    ← 同上
```

新方案采用**窄带 smoothstep**（只在断点附近 ±100 亿做三次平滑过渡，值与一阶导均连续），而不是全局线性插值（后者会改掉中段约 70% 样本的口径）。

标定结果（`tools/probe_turnover_kill_continuous.py`，40 个有效交易日）：

- 值连续性：相邻 1 亿最大跳变 **0.003375 pp**，约为旧阶跃 0.45pp 的 **1/133** → PASS
- 导数连续性：相邻步长最大二阶差 **0.000067 pp** → PASS
- 锚点一致性：6/6 与旧阶梯逐位相同（200/899→1.50、1200/1800→1.05、2200/5000→0.65）
- 逐日淘汰率差最大 **0.11 pp**，平均 0.04 pp
- 逐票差集：主阶梯 **0.05%**、放宽通道 **0.05%**（目标 <3%）→ PASS

落地方式：新增唯一口径函数 `core/strategies/fund_mv_utils.turnover_kill_threshold_pct(circ_mv_yi)`，`single_stock.py` 与 `adaptive_turnover_kill_threshold_relaxed` **同时**改为调用它，消除两份阶梯；`core/pool_manager/thresholds.py` 透出该函数并提供**退回旧硬阶梯**的容锛 import 兜底。死因文案统一为 `🧪股性呆滞(近5日均换手0.80%<底线1.28%,市值980亿)`，关键词不变。
