## 四、家里服务器专项（两份报告都没答好的部分）

你这次的关键变化是"**搬到家里服务器 7×24**"，这引出 8 个工程问题，必须一起解决：

| # | 问题 | 建议 |
|---|---|---|
| 1 | **Windows 还是 Linux** | 家里服务器若是 Windows → 用**计划任务 + 现有 bat 看门狗**（不要上 Docker，两份报告都反对，我也反对）；若是 Linux → `systemd` + `Restart=always` |
| 2 | **断电/重启恢复** | BIOS 设"来电自启" + UPS（哪怕是入门级 500VA）→ DuckDB 在 WAL 状态被硬断是最容易坏库的场景 |
| 3 | **远程查看，绝不开公网端口** | Streamlit 绑 `127.0.0.1`，用 **Tailscale / ZeroTier** 组网访问。**不要做端口映射** —— 这是自用系统最大的安全风险 |
| 4 | **单写者互斥** | 服务器上**默认只跑 daemon**，UI 按需启动；启动前脚本先探 `process_orchestrator` 的 sentinel 锁，避免自己撞锁 |
| 5 | **DuckDB 内存/线程** | 32G 内存建议 `memory_limit=8GB`、`threads=4~6`，留出给 pandas/向量化 |
| 6 | **磁盘与备份** | DuckDB 会持续增长；保留 N 份轮转备份 + 每周一次 `VACUUM`/压缩（已有 `weekly_db_maintenance_orchestrated.py`），并监控剩余空间 |
| 7 | **时区固定** | `Asia/Shanghai` 写死，不要依赖系统区域设置；日历静态化后不再联网 |
| 8 | **日志与告警** | 日志按日轮转；daemon 每 5~10 分钟心跳，每天早上 07:00 推一条"过去 24h 摘要"（跑没跑、扫了几拍、命中几条、库多大）→ **这条比任何新策略都值钱** |
