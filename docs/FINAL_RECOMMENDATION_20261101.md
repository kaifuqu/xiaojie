## 一、我和朋友的分歧（用代码证据说话）

### 分歧 1：他把「组合级风控」放 P0-1，我认为要往后挪半步

**他的前提**：小杰有持仓，只是缺组合视角。
**代码事实**：`core/paper_trading/schema.py` 是**单个模拟账户**（`paper_account` 单例），且 `core/paper_trading/engine.py:6` 明确只消费 **P3/P4** 两池。
**结论**：组合体检**现在能做**，但体检出来的是「模拟盘组合」，不是你真实管钱的组合。
**我的建议**：
- 组合体检**保留在第一批**，但定位改成「**模拟盘组合体检**」，别宣传成"管钱风险"
- 若真要管真实持仓 → 必须先建「真实持仓台账」（新表：成交流水/持仓/成本），这是独立一件事，排第三批
- 否则你就是在给一个只有 P3/P4 信号、120 条样本 7 个交易日的模拟账户，做"集中度/VaR/相关性"——**统计上不成立**

### 分歧 2：他把「Docker 化 + 开机自启」列为根治办法，我反对 Docker

**他的建议**：Docker 单容器 + 计划任务是"根治办法"。
**代码事实**：无 `Dockerfile`、无 `docker-compose.yml`；部署是 `start_server.bat` / `start_daemon_24x7.bat` / `deploy_new_machine.bat`，Windows 原生。
**我的判断**：
- DuckDB 单文件 + Windows 单机 + `.bat` 双击启动，是**当前最稳的部署形态**（复制文件即迁移，`DEPLOY_NEW_MACHINE.md` 已验证 4 步）
- Docker 化对个人单机系统 = **用重锤敲钉子**：要处理 Windows 路径挂载、DuckDB 单写者跨容器锁、中文路径编码——每一个都是新坑
- **真正的需求只有一条：开机自启**。用 **Windows 任务计划程序**（`schtasks /create /sc onstart`）5 分钟搞定，收益是 Docker 的 90%，成本是 5%
- **建议**：把"开机自启"从 P2-14 提到**第一批**（它其实是可用性阻塞：电脑重启后系统就死了没人知道），把"Docker 化"降为**明确不做**

### 分歧 3：他把「K 线图」的技术前提说错了

**他的原话**：「你已经在 strategy_effectiveness_panel 里用过 plotly，技术上很轻」。
**代码事实**：`ui/strategy_effectiveness_panel.py:16` 是 `import altair as alt`；`requirements.txt` / `requirements.lock` **都没有 plotly**。
**结论**：加 K 线有两条路，成本不同——
- **路线 A（零新依赖）**：用**已有的 altair** 拼蜡烛图（`mark_bar` + `mark_rule` 画影线），交互弱但能用
- **路线 B（加一个包）**：`pip install plotly`，蜡烛图 + 缩放 + 画线工具齐全，但要多锁一个版本、多一个前端渲染路径

**我的建议**：**先走 A**（altair 已在依赖里，零风险），个股深挖页真要用起来（缩放/画趋势线）再上 B。
朋友这条判断的价值在「K 线是体验最大落差」——这点我同意；但"技术上很轻"这个前提是错的，别被误导成"今天就能上"。

### 分歧 4：他把「完美图形匹配（DTW）」放 P1，我认为要降到 P2

**他的理由**：全新信号维度，小杰完全没有。
**我的判断**：
- B1 相似度匹配的**前提是「成功案例库」质量**。而案例库的定义（"什么算成功启动"）依赖 **T+N 前瞻收益口径**——正是当前 G1（无样本外、口径未扣费）要修的
- 在口径没修好前建案例库 = **用有偏差的标签训练匹配器**

### 分歧 5：他把「多智能体 AI 研究」放 P1，我认为降到 P2

**他的理由**：AI 研究深度是你最该升级的方向。
**我的判断（这条最重要）**：
- 现在 103~120 条信号、5~7 个交易日、**所有战法的 Wilson 95% 置信区间都覆盖 50%**（你 `LAUNCH_AUDIT_20261018.md` 自己的结论：没有一条战法能被证明优于抛硬币）
- 在「信号本身没被证明有效」时，升级 AI 解释 = **给不准的信号配更漂亮的说明书**
- 多智能体（4 分析师 + 辩论 + 风险评审 + 组合经理）是**改 prompt 工程 + 多轮调用 + 结构化输出 + 落地 schema** 的复合工程，且它的价值**完全依赖信号准不准**
- **建议**：第一批~四批只做**轻量一步**——把单 DeepSeek 的「一句话 50 字建议」改成「**多头 3 条 / 空头 3 条 / 裁决 1 句**」三段结构化输出，并把三个字段写进 `signal_log`（这样三个月后能统计"哪种多头理由的胜率高"）。**完整九智能体不做**（他的避坑清单也说了别一次上九角色）

### 分歧 6：「留一法评估」的对象要改

**他的建议**：「28 个 P1 评分因子正好适用留一法评估（逐个去掉看共识 IC）」。
**技术问题**：P1 是**加权求和**（`score_calibration.compute_p1_multi_dim_smooth_score`），去掉一个子项 = 改了总分尺度，不是干净的消融。
**建议**：
- 留一法的对象换成 **31 条原子战法**（`strategy_id_registry` 里的 P2-xx~P5-xx），而不是 P1 子评分项
- 因为战法是**可独立开关的布尔/分值贡献**，禁用一条战法看整体胜率变化，才是干净的边际贡献
- P1 子项的信息量应该用**横截面 IC + t 值**评估（每个子项分 vs T+N 收益的秩相关），而不是留一法
