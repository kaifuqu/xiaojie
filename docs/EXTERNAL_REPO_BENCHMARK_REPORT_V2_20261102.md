## 0. 方法与口径

### 0.1 我读这 13 个仓库的方法

对每个仓库，我只问三个问题，不做 README 复述：

1. **定位层**：它到底替谁解决了哪一类"不确定"？
2. **机制层**：它靠**哪一个具体机制**解决的？这个机制是"工程约定"（可以照搬）还是"另一套资产类别的前提假设"（照搬会出事）？
3. **落地层**：这个机制搬到小杰的**哪个文件、哪一行附近的逻辑**？要花多少工？会不会破坏你现有的策略语义、评分权重、闸门？

| 分类 | 含义 | 处理方式 |

## 1. 执行摘要

### 1.1 一句话结论

> 你缺的不是策略数量（31 条战法 + 5 档过滤已经够厚），而是**一条能证明策略有效性的证据链**。13 个仓库里真正值得抄的，全都集中在"把不确定变确定"这件事上：**数据可信（aktools / tick-stock-panel）、回测诚实（hikyuu / gs-quant / Vibe-Research）、样本外验证（hikyuu / tick-stock-panel / augur）、执行语义正确（hikyuu / day-trader-skill）、证据留痕（augur / gs-quant）**。其余花哨功能（多市场、Level-2、AI 实控）在你的场景里是负收益。

1. **选股是有效的**（跑赢基准），β 暴露是主要亏损来源 —— 样本集中在 2026 年 8~10 月的一段回落里，你选出来的票跟着大盘一起跌，但跌得比大盘少。

### 2.5 实测到的三个"沉默故障"

### 3.4 fasiondog/hikyuu —— 全仓最值得精读的一个，价值在"交易语义"

**定位**：C++ 内核 + Python 绑定的量化框架。它不是选股器，是**"如何诚实地模拟一次成交"的教科书**。

**关键机制（逐条都是能直接治病的东西）**

| 机制 | 具体做法 | 对应你哪个病 |
|---|---|---|
| **槽位模型** | `EV/CN/SG/MM/ST/TP/PG/SP` + `SE/AF/MF`，把"环境/条件/信号/资金管理/止损/止盈/持仓/支持"拆成独立槽 | 你的策略把"信号"和"仓位/止损/止盈"耦合在一起 |
| **次日成交延迟** | `buy_delay` / `sell_delay` 默认 1，即**当日信号次日开盘成交** | 你回测用 `fwd_arr` 未来**收盘价**算收益 → 系统性高估 |
| **一字板/停牌递延** | 涨跌停或停牌无法成交时自动递延，超过 `max_delay_count` 放弃 | 你回测**完全没有**涨跌停成交约束 |
| **滑点夹逼** | 成交价必须落在当日 `[low, high]` 区间内 | 你的模拟盘/回测都没有滑点夹逼 |
| **成本逐项 `CostRecord`** | 佣金 / 印花税 / 过户费**买卖分开**记录 | 你有 `paper_trading/fees.py` 但回测不用它 |
| **除权除息** | `updateWithWeight` 统一处理复权事件 | 你有前复权，但缺"复权因子变更日"标记 |
| **Null 语义** | 除零/零方差/全缺失 → NaN，**绝不写 0.0**；聚合只累加有限值 | 这是数据污染的**根因级**设计 |
| **组合即策略** | `PF_SignalAggregate` / `PF_Simple` / `PF_WithoutAF` —— 组合不是"策略之上再加一层"，组合本身就是策略 | 你的"跨池加权"散在 pipeline 里，没有独立可回测的组合对象 |
| **16000+ 断言** | 1300+ guards + 1600+ doctest | 你 0 个测试 |

**可借鉴 → 小杰落点（这是本报告的最高优先项）**

1. **统一成交口径**：把 `paper_trading/fees.py` 的 `CostRecord` 抽成 `core/execution_model.py`，**同时被** `backtest_runner.py` 与 `paper_trading` 引用。这一件事同时消灭"洞 2（模拟盘 0 成交）"和"回测不诚实"两个问题。
2. **`buy_delay=1`**：回测必须改成"信号日 T 收盘确认 → T+1 开盘买入"，这与 A 股 T+1 和你的盘尾/盘后档位天然吻合。现在 `run_painpoint_backtest` 用 `fwd_arr` 未来收盘价，**等于用了未来信息**。
3. **涨跌停不可成交**：一字涨停买不进、一字跌停卖不出，这是回测虚高的最大来源之一。你已有 `limit_quality_3d.py` 判定封板质量，可以复用它做"是否可成交"。
4. **Null 语义审计**：全仓搜索 `fillna(0)` / `or 0` / `if not x: x=0`，凡是"缺数据被当成 0 分/0 量"的地方，都是选股偏差来源（缺数据的票被系统性低估）。
5. **组合对象化**：把"跨池加权 + T+1 归因"从 `pipeline.py` 抽成一个可回测的 `Portfolio` 对象。

**不该照搬**：hikyuu 的 C++ 内核、HDF5/MySQL/ClickHouse 存储、它的指标 DSL —— 你的 DuckDB + pandas 组合已经够用，换内核是纯亏。

**落地建议**：成交语义 = **A 直接可借鉴（最高优先）**；组合对象化 = **B 需本地化改造**；内核/存储 = **D 不建议**。

## 8. 风险与红线

| 风险 | 说明 | 对策 |
|---|---|---|
| **改成交口径会让历史业绩"变难看"** | 这是对的，但心理冲击大 | 新旧口径**并列显示**，报告里明确"旧数字含未来信息" |
| **样本量极小（120 条信号 / 7 个交易日）** | 任何统计结论都不可靠 | n<30 一律标注"样本不足"；先养 60 个交易日样本再谈调权 |
| **11 张空表让部分策略"结构性空转"** | 龙虎榜/炸板/竞价快照策略拿不到数据还照跑 | fail-closed：数据缺失时该策略标记"数据不足·未生效"而非输出空结果 |
| **单写者锁** | 任何并发写都会炸库 | 所有新脚本只读连接；写操作走 daemon 唯一通道 |
| **无版本控制** | 改坏了无法回滚 | 每批改动前整目录备份；建议加 `.gitignore` + 本地 git（不做 push） |
| **`config.yaml` 密钥明文** | 你已确认仅本机运行，风险可接受 | 若要外置，用环境变量 + `.env`；报告与日志永不打明文 |
| **不许删业务代码** | P2-05 / P4-08~11 已从注册表摘除但文件保留 | 保持现状，只加"retired"标记 |
| **`fillna(0)` 类数据污染** | 缺数据被当 0 分，系统性低估 | 全局审计，改 NaN 语义（只改缺失处理，不改阈值） |
